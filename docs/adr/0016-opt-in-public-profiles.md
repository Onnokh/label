# Opt-In Public Profiles with Handles

Sleevy will let an Account publish a **Public Profile** at `/u/{handle}`, showing a **Handle**, a **Reading Activity** grid of daily save counts, and the Saved Items held by its **Published Folders**. A Handle is claimed when the profile is first turned on and lives in a dedicated one-to-one profile record rather than on the auth user, because a Handle is a product identifier and not a credential; the record survives turning **Profile Visibility** back off so a private Account keeps its Handle reserved, and only account deletion releases it. Handles are 3–30 characters of `a–z`, `0–9`, `-`, and `_`, are stored lowercase, exclude a reserved list that protects existing and future root paths, and are unique through an index on `lower(handle)`, following the convention already used for Folder names. Publishing is per Folder and explicit: a Saved Item is public when Profile Visibility is public and the Saved Item sits in a Published Folder, and that rule is resolved in SQL when the public list is read rather than denormalized onto rows. Turning Profile Visibility on therefore publishes nothing by itself, and a Saved Item filed in no Folder is never public, so a capture that files nothing publishes nothing. Sleevy considered and rejected the inverse — publish the whole library once the profile is on, with per-item and per-Folder exceptions to withhold — because it asks a person to audit an entire existing library to find what they would not want seen, and gets the default wrong in the direction that cannot be undone: a leak is permanent in a way an unpublished Folder is not. One audience decision per Folder is a thing someone can hold in their head, and it reuses a grouping they already made for their own reasons. A separate publishable Collection object was rejected too, as a third organising concept beside Folder and Tag that earns nothing the Folder flag does not. Because publishing is a deliberate act on a container the Account already curates, no delay, review screen, or per-item marker is needed: unpublishing a Folder withdraws it at once. Identity on the page is the Handle alone: no display name, no bio, and no avatar, so Sleevy never republishes a Google profile image or makes every visitor request one.

**Reading Activity** counts saves only, never reads, and counts first captures only, bucketed by Saved Item creation time in UTC across a rolling 52 weeks. Last-saved time is deliberately not used, because a **Duplicate Save** would silently rewrite the past every time an old Link returns through **Renewed Intent**, and per-viewer timezone bucketing is deliberately not used because it would give every visitor a different response and destroy shared caching. The grid counts every Saved Item, including those outside a Published Folder, with no switch to hide it, on the reasoning that a count is not a URL and a graph restricted to published items would be too empty to be worth building. Public reads are served by a new unauthenticated REST group — profile, activity, paged items, and the indexable-Handle listing the sitemap walks — that returns 404 for an unknown Handle and for a private Account alike, so the API never discloses that a Handle exists. Those endpoints return a separate public Saved Item representation defined as an allow-list rather than reusing the existing Saved Item DTO, so that Folder name, Source name, Capture Channel, read state, and the internal Saved Item identifier stay private and no future field leaks by default. Because these routes carry no API Key, the **API Key Rate Limit** cannot apply and per-IP limiting is added, keyed on the Cloudflare connecting-IP header, which is the only trustworthy client address behind the production proxy chain; the Web Companion forwards the visitor's address when it renders a page server-side, so one budget covers both arrival paths. Search indexability is decided in the API — an Account at least 7 days old with at least 5 public items — and returned as a boolean so the web layer renders a robots directive from a value and owns no part of the rule, which keeps that decision inside an existing tested seam and leaves no reason to introduce test infrastructure for the web app. Public pages use real paged URLs rather than infinite scroll, which a crawler cannot reach, carry `rel="ugc nofollow"` on every user-published outbound link so Sleevy is not worth targeting for link spam, and are cached for five minutes at the edge, which the page can afford because its markup never varies per viewer: a signed-in visitor's Save button attaches after the cached HTML lands, and those saves record a new `public-profile` **Capture Channel**. The existing iOS client decodes Capture Channel as a plain string, so adding the value needs no client release ordering.
