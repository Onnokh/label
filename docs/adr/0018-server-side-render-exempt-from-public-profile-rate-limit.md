# A Server-Side Render Is Exempt from the Public Profile Rate Limit

Sleevy will let the web server identify its own render of a public page with a shared secret, the **Render Token**, and will charge that request nothing against the **Public Profile Rate Limit**. ADR 0016 gave the public group a per-address budget of 60 requests a minute and had the Web Companion forward the visitor's address so one budget would cover both arrival paths — a visitor reading the page and a visitor calling the API. That turned out to refuse pages to readers who had done nothing wrong: rendering one Public Profile reads three **Public Profile Endpoints**, so a page view cost three of that visitor's sixty, and twenty views in a minute exhausted the budget and answered 429 to somebody who was only reloading. A render is not a third party. It is this deployment's own web server, reachable only inside the deployment network, and the same reasoning that already lets the API trust it to state CF-Connecting-IP lets it state who it is. A request carrying the Render Token therefore takes no budget and reports no budget headers, while a request with a wrong token or none is a public API client and is counted exactly as before; with no Render Token configured nothing is exempt, so a deployment that never sets one keeps the old behaviour. The token is supplied only through the `INTERNAL_RENDER_TOKEN` environment variable, held by both services, and is never committed. Raising the limit was considered and rejected: the number was not wrong, and a larger one would have hidden the fact that the render path was drawing on a budget meant for third parties while leaving the same failure waiting at a higher traffic level. Bucketing renders separately by address was rejected too, as a second budget that still refuses a page when it runs out.

What bounds the render path is the cache on the page itself, not a budget on the API behind it — and this is where the intent recorded in ADR 0016 was found not to be in force. The Public Profile page has declared itself cacheable for five minutes since it shipped, on the reasoning that its markup never varies per viewer, but Cloudflare ignores `Cache-Control` on HTML and JSON unless a Cache Rule says otherwise, so every visitor was still costing one render and three origin reads. A Cache Rule now makes `/u/*` eligible for cache. Two properties of that rule are load-bearing and are the ones to check whenever it is edited. Its Browser TTL must respect the origin, so that unpublishing a **Published Folder** still withdraws it within the five minutes ADR 0016 promises rather than sitting in browser caches nobody can purge — an early version of the rule overrode this to four hours, which is a window no purge can reach. Its Edge TTL must respect the origin too, so that the not-found answer, which the page deliberately serves without a cache header, stays uncached and a newly claimed **Handle** works immediately rather than after the window expires. A longer edge window is a reasonable thing to want, but it belongs in `PAGE_CACHE_SECONDS` and in this record, not in a dashboard setting that quietly disagrees with both. The public API is deliberately left uncached at the edge: a **Server-Side Render** reaches it across the deployment network rather than through Cloudflare, so caching it would not remove the reads a page view causes, and its responses vary on `Origin` for CORS, which Cloudflare does not vary on outside Enterprise — a cached copy would pin one allowed origin and hand it to callers from another. Where the two mechanisms overlap they are complementary rather than redundant: the cache removes the ordinary visitor from the origin entirely, and the exemption keeps the page serving on a cache miss, for a crawler sweeping many profiles, and for a hand-edited page number.
