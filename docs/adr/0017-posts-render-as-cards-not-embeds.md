# Posts Render as Cards, Not Platform Embeds

Sleevy will treat a short social message as its own **Type**, called **Post**, and render it on a **Public Profile** as a **Post Card** that the page itself draws. A saved tweet arrived as a `website` whose **Link Metadata** title held the entire message, so a client had nothing to tell it that the title was the words themselves rather than a headline for them: the Public Profile set a whole tweet as a headline, collapsed the writer's paragraph breaks into one run of text, and then showed a **Preview Summary** underneath that restated the message in more words than the message used. The Type is decided at capture from the URL alone — one message on a platform a provider can resolve, which today means an x.com or twitter.com status, while a profile page or a platform home page stays a plain Link. Classification and provider support are extended together on purpose: a Post with no **Link Author** and no words of its own reads worse as a Post than as a Link, so a platform is only classified once something can resolve it. The Link Author — a name, a handle, and an avatar address — is new on Link Metadata and is filled only by a provider that states the writer; page markup is deliberately not read for it, because the common author meta tags carry a profile URL as often as a name. **Site Name** keeps holding the author handle for a tweet so the **Native iOS App** and the **Library** show what they showed before, which makes the Link Author additive rather than a migration. **Link Enrichment** writes no Preview Summary for a Post and records that stage as skipped, so a job still accounts for every stage; because Tags and the summary come from one AI call, a Post is still tagged and what is dropped is the summary alone. The three Link Author properties are published on the public Saved Item representation, which widens the allow-list of ADR 0016 by a deliberate act rather than by default: all three come from the platform's own public payload for a Link the Account chose to publish, and the contract test that guards that list was changed alongside them.

A Post is rendered as markup the Public Profile produces, never as a platform embed script. An embed from X or a syndication-backed component would look more familiar and would carry replies, media, and quoted posts for free, and it was rejected anyway, because a Public Profile is server-rendered, cached at the edge, indexable, and identical for every viewer: an embed would put the message behind third-party JavaScript, so a crawler would index a page whose main content is missing, a reader with scripts blocked would see an empty card, and every visitor would fetch from a third party that learns who reads what. Drawing the card locally keeps the words in the HTML, which is the property the whole page is built around. The cost is accepted and named: a Post Card shows the message, the writer, and one image, and it does not show replies, threads, quoted posts, polls, or engagement counts, and a reader who wants those follows the link. A Post Card sets the message at reading size with its line breaks kept and clamps it, because a long message that ran unclamped made one card as tall as four; a **Link Card** leads with the title instead, because for every other Type the title is a headline for something else. Both carry the same image beside the text rather than above it, so a Post keeps the rhythm of the list, and both are one link over the whole card rather than several links to one address, which a screen reader would otherwise read out one after another. This trade is worth revisiting for a platform whose value is the picture rather than the words, where a thumbnail loses the point of the Post.
